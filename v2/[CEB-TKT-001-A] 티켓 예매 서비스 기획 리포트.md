## 1. 개요·배경

### 1.1 추진 배경

- **10월 15일 또는 16일 V01D 쇼케이스** 개최가 예정되어 있으며, 이 일정을 맞추려면 **9월 중후반에는 티켓 판매가 오픈**되어야 한다.
- 전자결제(PG) 가맹 심사는 2주~2개월로 기간이 미정이라 쇼케이스 일정에 맞출 수 없다. 따라서 1차 오픈은 **PG 없이 "통장 입금(계좌이체) 확인 → 티켓 지급"** 방식으로 간다. PG 연동은 이후 단계에서 진행한다.
- 티켓 판매에는 법령상 준비 의무(예매자 본인확인, 암표·부정판매 신고 창구와 24시간 이내 조치, 현금영수증 발행)가 따르므로, 기능 기획과 법적 요건을 함께 설계해야 한다.

### 1.3 요구사항 요약 (2026.08.28 접수)

1. 티켓 판매 시 **본인확인 의무** — 중복가입확인정보(DI) 값을 DB에서 관리, 중복 가입 불가. 다날 제공 본인확인 기능이 있으면 그것으로 대체
2. **암표·부정판매 신고 창구** — 통보 접수 시 24시간 이내 정보통신망 노출 차단 조치 + 수사기관 제출
3. **티켓 재고 4분류** — 유료 판매분(`PAID_SALE`) / 셀러버스 당첨자분(`CELEBUS_WINNER`) / IX 초대분(`IX_INVITATION`) / 운영 예비분(`OPERATION_HOLD`) ※ 코드 표기는 요구사항 원문 인용이며, 본문에서는 한국어 명칭을 사용한다
4. **무통장입금 플로우** — 주문 시 "입금 확인중" 상태로 등록하며 해당 수량을 선점(reserve). 입금 계좌번호는 유저가 다시 확인 가능. 입금 허용 마감은 **당일 자정(00시)**, 초과 시 선점 자동 취소. 자정 이후 입금된 코너케이스는 **환불 후 재주문** 안내
5. **실명 매칭** — 본인확인 실명과 입금자 실명이 일치해야 티켓 지급. 현금영수증 발행을 위해 전화번호·DI 저장
6. **취소·환불** — 요청 후 24시간 이내 처리
7. PG 연동은 이후 단계

### 3.2 팬 플랫폼·본인확인 UX 관찰

- **위버스 선예매**: 멤버십 실명 = 예매 사이트 실명 = 입장자 실명의 3단 일치를 요구. 실명 이중 대조는 팬 후기에서 "포기할 뻔"이라는 표현이 나올 정도로 UX 마찰이 크다 → CELEBUS는 앱 계정 본인확인 실명 하나로 일원화하는 것이 유리.
- **1인 매수 제한**: "본인 포함 1인 2매"가 흔한 패턴.
- **본인 입장 확인**: "예매자 본인 명의 신분증 미확인 시 입장 제한, 미지참 책임은 본인, 당일 환불 불가"가 표준 고지 문구. 다만 안면인식 오류·미성년 자녀 입장 거부 등 **소비자 분쟁 사례가 다수 보도**되어, 강한 본인 입장 정책은 사전 고지 강화(예매 단계 동의 체크 + 알림 재발송)와 함께 도입해야 한다.
- **모바일 티켓**: 인터파크·위버스샵 모두 캡처 화면 입장 불가·양도 불가 고지. 위버스 콘서트는 "입장하기" 버튼이 **공연 시작 20~60분 전에만 활성화**되는 시간 게이팅 방식 — 구현 난이도 대비 효과가 좋아 1차 오픈에 적합.
- **부정예매 제재**: 인터파크는 부정거래 확인 시 사전 통보 없이 예매 취소 + 최대 30% 수수료 부과 + 계정 영구 제한을 약관에 명문화.

## 4. 서비스 설계

### 4.1 도메인 모델

멀티아티스트 운영 가이드의 "아티스트별 + 공연 단위 추가 분리" 원칙에 따라 최상위를 **공연**으로 둔다.

```text
아티스트 (V01D 등)
 └─ 공연 (쇼케이스·콘서트·팬미팅 1건)          ← 환불 정책·판매 기간·안내문을 공연 단위로 설정
     └─ 회차 (10/15 공연, 10/16 공연 …)        ← 일시·장소·입장 시간
         └─ 티켓 재고 (회차별, 4분류 배정)
             ├─ 유료 판매분        — 앱 내 유료 판매 대상
             ├─ 셀러버스 당첨자분  — 래플 당첨자에게 지급
             ├─ IX 초대분          — IX(소속사) 초청 명단에 지급
             └─ 운영 예비분        — 장애·좌석 문제 대응, 판매하지 않음
```

- **주문**: 회원이 유료 판매분에 대해 예매를 신청한 단위. 매수·금액·입금 기한·입금자 확인 정보를 가진다.
- **티켓(입장권)**: 지급이 확정된 입장 권리 1매 단위. 주문과 분리해 관리한다 — 당첨자분·초대분은 주문 없이 티켓만 발급되고, 유료 판매분은 "주문 확정 → 티켓 N매 발급"으로 이어지기 때문이다. 티켓에는 소유 회원·회차·상태·입장 확인(QR) 정보가 귀속된다.
- **입금 확인 건**: 운영자가 통장 입금 내역을 주문과 매칭한 기록. 입금자명·금액·입금 일시·매칭 결과를 남긴다.
- **신고 건**: 암표·부정판매 신고 접수 단위 (§4.5).

**재고 4분류 운영 규칙**

| 항목 | 규칙 |
| --- | --- |
| 배정 | 회차 생성 시 4분류 수량을 배정. 4분류 합계 = 회차 총 좌석 수 |
| 재배정 | 판매 개시 후 분류 간 수량 이동은 BO에서 운영자 이상 권한으로만 가능하며 활동 로그에 기록 (예: 판매 부진 시 운영 예비분 → 유료 판매분 전환) |
| 판매 노출 | 앱에는 유료 판매분의 "판매 가능 수량"만 반영. 나머지 3분류는 노출하지 않음 |
| 운영 예비분 | 판매·지급 모두 차단. 장애·좌석 문제 발생 시 개별 회원에게 수동 지급(사유 필수 입력) |

### 4.2 주문·티켓 상태 흐름 (무통장입금 1차 오픈 기준)

```text
[주문 상태]

  주문 생성 ──────────► 입금 확인중 ────────► 입금 확인 완료 ─────────► 지급 완료
  (매수만큼 재고 선점,    (유저: 입금 계좌·금액·   (운영자 액션 ①            (운영자 액션 ②
   입금 안내 노출)         기한 재확인 가능)        입금 매칭+실명 일치 확인.   티켓 수동 지급 처리 —
                                                  지급 대기 상태)            티켓 N매 발급,
                                                                            현금영수증 발행)
        │                        │        │
        │                        │        └───► 확인 보류 (실명 불일치·금액 불일치 → 운영자 수동 확인 큐, §4.4)
        │                        │
        ▼                        ▼
    주문 취소(유저)         기한 만료 자동 취소
                            (당일 자정 경과 시 선점 재고 원복)

  지급 완료 ──► 취소 요청(유저) ──► 환불 처리중 ──► 환불 완료 (24시간 이내 처리, 티켓 회수)
```

**핵심 규칙**

| # | 규칙 | 비고 |
| --- | --- | --- |
| 1 | 주문 생성 시점에 매수만큼 유료 판매분 재고를 **원자적으로 선점**한다. 잔여 수량 부족 시 주문 자체가 생성되지 않는다 | 초과 판매(오버셀) 방지. 동시 주문 경합은 서버에서 재고 차감 시점에 판정 |
| 2 | 입금 기한 = **주문 당일 자정(23:59:59, KST)**. 자정 경과 시 서버가 자동으로 주문을 취소하고 선점 재고를 원복한다 | 앱은 남은 입금 시간을 카운트다운으로 노출 |
| 3 | 결제 화면 이탈·앱 종료 후에도 유저는 **주문 내역에서 입금 계좌번호·금액·기한을 재확인**할 수 있다 | 요구사항 4 반영 |
| 4 | **자정 이후 입금(코너케이스)**: 주문은 이미 자동 취소된 상태 → 입금 건을 "매칭 대상 없음"으로 분류하고 전액 환불 처리 후, 유저에게 재주문을 안내한다. 단 **잔여 재고가 남아 있으면 운영자 재량으로 주문을 구제 확정할 수 있는 예외 분기**를 열어 둔다 (해외 예매 시스템의 기한 만료 유예 처리 관행 — §10 외부 레퍼런스) | 환불 계좌 확인이 필요하므로 BO 수동 처리 큐에서 관리 (§5). 구제 확정 시 활동 로그에 사유 기록 |
| 5 | 취소·환불 요청은 접수 후 **24시간 이내 처리**를 원칙으로 한다. 처리 = 티켓 회수(입장 무효화) + 환불 이체 + 현금영수증 취소 발행 | 공연 임박 시점의 취소 수수료 정책은 §2 환불 규정에 따라 공연 단위로 설정 |
| 6 | 1인당 구매 한도: 본인확인된 계정 1개당 회차별 **최대 4매** (§1.4 확정). 공연 단위 설정값으로 두어 공연별 조정 가능 | 중복가입 차단(§4.3)과 결합해야 실효성 있음 |
| 8 | **입금 확인과 티켓 지급은 별도의 운영자 액션**이다 — ① 입금 확인(대조·실명 확인) 후 주문은 "지급 대기"가 되고, ② 관리자 화면에서 티켓 지급 처리를 해야 티켓이 발급된다 (§1.4 확정 플로우) | 지급 전 재검토 구간 확보. 지급 처리 시 현금영수증 발행 |
| 7 | 주문·티켓은 처음부터 별개 단위로 관리한다 — 주문 = 결제·환불·정산 단위, 티켓 = 입장 권리 1매 단위 | "1주문 다수매 중 일부만 환불", "당첨·초대분의 무주문 발급" 요구를 수용하기 위한 업계 표준 구조 (§10 외부 레퍼런스) |

> 설계 메모: 재고 선점 만료는 별도 정리 작업 없이 "조회 시점에 만료된 선점을 잔여분으로 취급"하는 방식으로 시작하면 초기 구현이 단순하다. 선점 시간이 카드 결제 대비 긴 무통장입금 특성상 만료 판정과 자동 취소 처리는 여유 있게 설계한다.

### 4.3 본인확인·중복가입 차단 설계

```text
[최초 1회 — 티켓 기능 진입 시]

앱: 예매 시작 ──► 본인확인 필요 안내 ──► 간편인증 (PASS·카카오·토스·네이버 등 인증 수단 선택)
                                              │
                                              ▼
                              실명·생년월일·전화번호·DI 수신
                                              │
                              DI 중복 검사 ──┬── 미중복 → 회원에 본인확인 정보 저장, KYC 상태 = 인증 완료
                                             └── 중복   → "이미 본인확인된 계정이 있습니다" 차단 안내
                                                          (기존 계정 안내 + 고객센터 문의 경로)
```

| 항목 | 설계 |
| --- | --- |
| 인증 수단 | **간편인증** — PASS·카카오·토스·네이버 등 복수 인증 수단 제공 (§1.4 확정). 채택 사업자는 **본인확인기관 지정 + DI 반환 가능** 조건으로 선정 (연동 대행사 경유 시 복수 수단 일괄 제공 가능 — 계약 검토) |
| 저장 항목 | 실명, 생년월일, 전화번호, DI(중복가입확인정보). **주민등록번호는 저장하지 않는다** |
| 중복 차단 | DI 값에 유일성 제약. 동일인이 복수 계정으로 본인확인을 시도하면 차단 — "중복 가입을 통한 구매 불가" 요건의 구현 지점 |
| 시점 | 회원가입 시 강제하지 않고 **티켓 예매(또는 당첨 티켓 수령) 최초 진입 시** 요구 — 기존 회원 이탈 방지, 티켓 외 기능은 영향 없음 |
| USR 연동 | [CEB-BO-002]의 KYC 상태(미인증·인증 완료·반려)의 실체가 됨. 회원 상세에 본인확인 일시·실명·전화 표시(마스킹), DI는 화면 비노출 |
| 활용 | ① 중복가입 차단 ② 입금자 실명 매칭 기준값 ③ 현금영수증 발행 식별정보(전화번호) ④ 입장 시 본인 대조(공연 정책에 따라) |
| 보관·파기 | 수집 목적(본인확인·부정거래 방지·현금영수증)을 고지하고, 보관 기간·파기 규칙은 §2 개인정보 요건에 따라 법무 확정 |

### 4.4 입금 확인·실명 매칭 로직

```text
[운영자 일일 운영 사이클]

은행 입금 내역 (수시 확인/다운로드)
        │
        ▼
BO 입금 확인 큐: 미확인 입금 건 ↔ "입금 확인중" 주문 목록 대조
        │
        ├── 입금자명 = 본인확인 실명 AND 금액 일치  ──► "입금 확인" 처리 → 지급 대기 → "티켓 지급" 처리(별도 액션) → 지급 완료
        │
        ├── 금액 일치 + 입금자명 불일치(동명이인·가족 입금 등) ──► 보류 큐 → 유저에게 입금 확인 요청 알림
        │                                                            (앱에서 입금 일시·은행 제출 → 운영자 수동 대조)
        ├── 금액 불일치(과·부족) ──► 보류 큐 → 차액 안내 또는 환불
        │
        └── 매칭 대상 주문 없음(자정 후 입금 등) ──► 환불 대상 큐 (§4.2 규칙 4)
```

- 주문 시 앱이 **입금자명 규칙**을 강하게 안내한다: "반드시 본인확인하신 실명 '{실명}'으로 입금해 주세요. 다른 이름으로 입금하면 확인이 지연되거나 취소될 수 있습니다."
- 동명이인·가족 입금 대비 **백업 규칙**을 함께 안내한다: "부득이 다른 이름으로 입금해야 하면 입금자명을 '{실명}+주문번호 끝 4자리'로 입력해 주세요" — 가상계좌가 없는 지정계좌 판매의 실무 표준 규칙 (§3.4). 자동 대조는 "금액 완전 일치 + 입금자명 일치(또는 백업 규칙 일치)"를 1차 조건으로 하되, **자동 확정은 하지 않고 운영자 최종 확인 클릭을 거치는 반자동**으로 운영한다 (오입금 리스크 방지).
- 입금 확인·보류·환불의 모든 처리 이력은 활동 로그에 남긴다.

### 4.5 암표·부정판매 신고 창구

기존 기억저장소 신고 처리 구조([CEB-BO-MEM-101] 신고 리스트 → [CEB-BO-MEM-201] 신고 상세·처리 → [CEB-BO-MEM-301] 차단 통합)를 이식하되, 법령상 시한 요건을 추가한다.

```text
[앱]                                  [BO]
신고하기 진입                          신고 접수 큐 (접수 시각 기록 → 24시간 시한 타이머 표시)
 ├ 신고 대상: 게시물·계정·외부 링크      │
 ├ 신고 사유: 암표 판매 / 매크로 의심     ├ 조치 ① 노출 차단 (임시조치) — 24시간 이내
 │           / 양도 권유 / 기타          ├ 조치 ② 증거 보전 (게시물 원문·작성자 정보 스냅샷)
 └ 증빙 첨부 (스크린샷·URL)             ├ 조치 ③ 수사기관 제출 기록 (제출일·기관·문서번호)
                                        ├ 조치 ④ 계정 제재 연동 ([CEB-BO-USR-501] 정지사유)
                                        └ 조치 ⑤ 티켓 무효화 (해당 티켓 특정 시)
```

- **조치 시한 관리**: 개정 공연법 계열 규정상 원칙 24시간, 문체부 고시 지정 사항은 **10시간 이내** 조치 의무가 있으므로(§2.1 #2), SLA 타이머는 **10시간 기준으로 보수 설계**하고 시한 임박 시 관리자 알림을 보낸다. 조치 완료 시각을 기록해 시한 준수 여부를 사후 감사할 수 있어야 한다. 야간·주말 접수 대응을 위한 운영 온콜 체계가 필요하다 (§8).
- 신고 접수 채널은 앱 내 신고 버튼 외에 **외부 통보(권리자·기관·문체부 통합 신고 누리집 경유) 수기 등록** 입력도 지원한다 — "통보를 받은 경우"가 법령 요건이므로 앱 내 신고에 한정하면 안 된다. 이용약관·공지에는 문체부 통합 신고 누리집(culture.go.kr/singo)을 외부 공식 창구로 병기한다 (§3.3).
- 개정 공연법은 판매 사업자에게 **부정거래 방지 기술적·관리적 조치 의무**를 별도로 부과하므로(§2.1 #1), 신고 창구 외에도 다중계정 차단(§4.3)·1인 매수 제한(§4.2)·거래 로그 보관을 "조치 의무 이행 항목"으로 함께 문서화해 두어야 한다.

### 4.6 당첨자·초대 티켓 지급 (래플·IX 연동)

| 경로 | 흐름 |

### 4.7 발권·입장 검증 (QR)

| 항목 | 1차 오픈 설계 | 근거 |
| --- | --- | --- |
| QR 방식 | 티켓별 서명된 일회성 코드 + **입장 스캔 시 서버 조회로 사용 여부 확인·즉시 사용 처리** | 위조 방지(서명) + 중복 입장 방지(서버 확인)의 표준 조합. 회전형(수 초마다 갱신) QR은 쇼케이스 규모에 과투자 — 확장 단계 검토 |

| 본인 대조 | 공연 정책에 따라 신분증 대조 병행 여부 설정. 대조 시행 시 예매 단계에서 고지 동의 필수 (§3.2 분쟁 사례) | 공연 단위 설정값 |
| 양도 | 1차 오픈은 **양도 전면 금지** 고지 + 위반 시 예매 취소·계정 제재 조항 약관 명문화 | 인터파크 부정예매 제재 관행 (§3.2) |

## A. 시즌 패스형 누적 트랙 (가칭 "CELEB PASS")

### 원리
배틀패스 심리: XP는 성과가 아니라 **참여**로 쌓인다 → 기록 못 깬 판에도 "뭔가 진행됐다"가 보장되어 매판 전력 압박을 완충. (레퍼런스: Royal Pass, 배틀패스 일반론, Monopoly Go 앨범의 완성 욕구)

### 시즌 주기
- **월간 시즌** (KST 1일 00:00 리셋) — 기존 `game_period_bounds('month')` 인프라 그대로 재사용. 월간 리더보드와 주기 일치.
- 시즌 키: `YYYY-MM` 문자열.

### XP 적립 규칙 (서버 계산 — 조작 불가)
- 판 제출 시: `xp = xpBase + floor(min(elapsed_sec, xpSecCap) / xpSecDiv)`
  - 기본값: `xpBase 10, xpSecCap 120, xpSecDiv 12` → 판당 **10~20 XP**
  - 점수·레벨 **무관** (성과 독립이 핵심). elapsed 기반 가산으로 "즉시 기권 스팸 파밍" 차단 (elapsed_sec은 서버 match 발급~제출 시각으로 이미 신뢰 가능)
  - `flagged`(의심) 판은 적립 제외 — 주간 보상과 동일 정책
- 일 상한(선택): `xpDayCap 300` (≈ 15~30판) — 과몰입 의무화 방지. 초기엔 off 가능.

### 레벨·보상
- 레벨당 필요 XP `perLevel 100` (선형), 최대 `maxLevel 30`
- 기준 체감: 일 3판(현 KPI 목표) 유저 → 월말 레벨 ~13, 일 7판 헤비 유저 → 30 근접
- 보상표 (config `pass.rewards[]`, 관리자 튜닝):

| 레벨 | 보상안 |
|---|---|
| 매 레벨 | CP 10 (기본 채움) |
| 5·10·15 | CP 30 + 하트 1 |
| 20 | **시즌 한정 테마** ← 옵션 2 채택 시 (스킨 시스템 첫 슬라이스) |
| 25 | CP 50 + 하트 2 |
| 30 | CP 100 + (시즌 배지/테마 변형) |

- **보상 범위 결정 필요**:
  - 옵션 1 (최소): CP·하트만 — 기존 원장·인벤토리 경제로 즉시 구현
  - 옵션 2 (권장): 레벨 20에 시즌 한정 테마 1종 — 보류 중인 스킨 설계안([[project-skin-system-design]])의 최소 슬라이스(장착 칼럼 + 보유 테이블 + 테마설정 연동)를 이번에 착수. "시즌 한정 위신 보상"이 패스의 견인력을 크게 올림

### UI
1. **결과 모달 "+N XP" 플라이업** — 가장 중요. 매판 무조건 +가 보이는 순간이 이 시스템의 존재 이유. 점수 카운트업 아래 패스 진행바 미니 표시
2. 홈 위젯: 미션 위젯 아래(또는 통합) 패스 진행바 + 현재 레벨 + [받기] 뱃지 — 접이식(미션 위젯 패턴 재사용)
3. 시즌 종료: 월초 첫 접속 시 시즌 결과 모달(`WeeklyResultModal` 패턴 재사용 — 최종 레벨·수령 요약·컨페티)
4. 미수령 보상은 시즌 종료 후 **7일 유예** 수령 가능(loss aversion을 처벌로 만들지 않기)

### DB (additive-first — 공유 DB 안전 수칙 준수)
- `game_pass_xp(player_hash, season, xp, updated_at)` PK(player, season)
- `game_pass_claim(player_hash, season, level)` PK 3중 — 중복 수령 차단 (미션 claim 패턴 동일)
- RPC: `game_pass_status(시즌·xp·수령 레벨 목록)` / `game_pass_claim_reward(level)` (서버 재검증 + 원장 `pass:시즌:레벨`)
- `game_submit_score` 재작성: 기존 로직 정확 재현 + XP upsert 1구문 추가 (026 재작성과 동일 방식, 배포와 원자적으로)
- config: `pass { xpBase, xpSecCap, xpSecDiv, xpDayCap, perLevel, maxLevel, rewards[] }` — mergeRemoteConfig obj 목록 추가 + 관리자 설정 폼 그룹

## D. 순항 구간 (성과 연동 관용)

### 원리
플로우 몰입은 그 자체로 고노력 상태 — 회복 구간 없는 반복이 번아웃의 직접 원인. Royal Match Butler's Gift/Super Duke처럼 **어려운 순간의 바닥을 잘라내고, 하루의 시작을 부드럽게** 만든다. 전부 config 게이트로 라이브 on/off·튜닝 가능.

### D1. 웜업 보너스 — 하루 첫 판 +15초 (전원 공정)
- KST일 기준 **첫 일반 매치 판**에 시작 시간 `+warmup.firstRunSec(15)` (60→75s)
- 판정: `/api/scores/start`가 오늘 해당 모드 제출 이력 조회 → 응답에 `warmup: true` → 클라 적용 + 인트로에 "☀️ 오늘의 첫 판 보너스 +15초" 배너
- **공정성**: 전원이 하루 정확히 1회 동일 혜택 → 일일 시드 랭킹 비교 가능성 유지
- 효과: "몸 안 풀린 첫 판에 최고기록 압박" 제거, 하루의 진입 장벽 하향

### D2. 라스트 스퍼트 (막판 구원, Super Duke형)
- 판당 1회: 타이머 0 도달 시점에 **현재 레벨 목표 진행도 ≥ 70%면 자동 +5초** (`grace { threshold: 0.7, sec: 5, perRun: 1 }`)
- 연출: "🔥 라스트 스퍼트!" 배너 + 타이머 골드 플래시 (기존 addTime 플라이업 경로 재사용)
- 하트 이어하기 **이전** 단계의 무료 관용 — near-miss 연구의 "아슬아슬한 실패 = 최대 좌절"의 바닥을 절단. 하트 소비와 역할 분리(스퍼트=무료 5초 1회, 하트=유료 30초 연장)
- 클라 구현(타이머 만료 훅) + moves 로그에 기록(`k:'g'`) — 리플레이 검증 호환

### D3. 연속 플레이 부스터 (옵션 — 결정 필요)
- 출석 스트릭 연동: streak ≥3일 → 일반 매치 시작 +5초, ≥7일 → +10초
- **트레이드오프**: 획득 가능성은 전원 동일하지만 당일 컨디션이 아닌 과거 출석이 랭킹 판에 영향 → 일일 시드 비교 공정성이 약간 흐려짐
- 대안: 부스터를 **아이템 매치 한정**으로 적용(랭킹 공정성 민감도 낮은 모드), 일반 매치는 D1만
- → 사용자 결정 대기

## G. 좌절 데이터 운영 (밸런스 계측 + 상시 프루닝)

### 원리
King 방식: "재미없는 좌절 구간"을 감으로 아닌 데이터로 찾아 상시 리밸런싱. Time to Abandon류 지표를 우리 구조(레벨 목표 곡선)에 맞게 계측 → 기존 관리자 설정 폼(levels.baseTarget/targetStep/bonusSec)으로 튜닝하는 운영 루프를 만든다.

### 데이터 추가 (additive)
- `game_scores.end_reason text` — `'timeout' | 'giveup' | 'spurt_timeout'`(스퍼트 후 종료) : 클라 제출 페이로드에 추가
- `game_scores.continues_used int` — 하트 이어하기 사용 수
- `game_scores.level_progress numeric` — 종료 시점 현재 레벨 목표 진행도(0~1) → near-miss율 산출 근거
- 셋 다 nullable 추가라 구버전 클라 제출과 호환

### 관리자 "밸런스" 화면 (대시보드 확장 또는 신규 탭)
RPC `admin_balance_stats(days)` (service_role, additive) — 최근 N일 집계:

| 지표 | 정의 | 좌절 신호 해석 |
|---|---|---|
| 레벨 도달 퍼널 | 판수 대비 레벨 N 도달 비율 (막대) | 특정 레벨에서 급락 = 목표 곡선 벽 |
| near-miss율 | 레벨별 `level_progress ≥ 0.8`에서 종료된 판 비율 | 높음 = 좌절 최대 구간 (스퍼트·bonusSec 튜닝 대상) |
| 기권률 | end_reason=giveup 비율 추이 | 상승 = 의욕 저하 조기 신호 |
| 이어하기 수락률 | continues_used>0 / 하트 보유 종료 판 | 하락 = "더 해봤자"라는 포기 심리 |
| 재도전 체인 | 동일 유저 10분 내 연속 판수 분포 | 긴 체인 다수 = "한판만 더" 압박 과열 |
| 일 판수 코호트 추이 | 유저별 일 판수의 주간 변화 (감소 코호트 수) | 판수 급감 = 피로 이탈 전조 |

### 운영 루틴
- 주 1회 밸런스 화면 확인 → `levels.*`·`grace.*`·`pass.*` 파라미터를 설정 탭에서 튜닝 (재배포 불필요 — 기존 config 인프라)
- A·D 배포 전후 비교가 가능하도록 **G를 먼저 배포해 기준선 확보**

## 진행 순서 제안

| 순서 | 웨이브 | 규모 | 이유 |
|---|---|---|---|
| 1 | **G** (계측 + 밸런스 화면) | 소 (additive 칼럼 + RPC + 관리자 화면) | 기준선 먼저 — A·D 효과 측정 가능하게 |
| 2 | **D1 + D2** (웜업·스퍼트) | 소 (클라 중심 + start API 1필드) | 저비용·즉효, config 게이트로 안전 |
| 3 | **A** (CELEB PASS) | 중 (DB 3종 + submit 재작성 + UI 3곳) | 가장 큰 효과, 보상 범위 결정 후 착수 |

각 웨이브는 기존 절차 준수: 로컬 검증 → 사용자 최종 테스트 → 승인 → 배포. DB 변경은 additive-first + 배포와 원자적으로(공유 DB 수칙).

## 사용자 결정 필요 사항

1. **A 보상 범위**: 옵션 1(CP·하트만) vs 옵션 2(레벨 20 시즌 한정 테마 = 스킨 시스템 첫 슬라이스, 권장)
2. **D3 연속 플레이 부스터**: 미포함 / 아이템 매치 한정 / 일반 매치 포함
3. **진행 순서**: G→D→A 제안 컨펌 (또는 조정)
4. A 세부 기본값(XP 계수·레벨 수·보상표)은 구현 시 config 기본값으로 넣고 배포 후 튜닝 가능 — 표의 초안값으로 시작해도 되는지
